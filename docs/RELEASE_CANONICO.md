# Entregas de Inkora: fuente única y control de regresiones

## Causa del incidente

La corrección de series se publicó desde un árbol divergente. El commit no identificaba los cambios locales: se enviaron archivos anteriores de interfaz y API junto con el arreglo. `_release_guides_prod` contenía funcionalidades recuperables, pero también versiones anteriores a los controles actuales de GRE, contingencia y paginación. Ni copiar esa carpeta completa ni publicar la raíz sin comparar resolvía el problema.

La única fuente para nuevas entregas es la raíz que contiene este documento, `backend`, `frontend`, `contracts` y `scripts`. Las carpetas `_release_*`, `_push_*`, `tmp`, fixtures, copias y respaldos nunca son fuentes de publicación.

## Puertas obligatorias

1. Registrar `git rev-parse HEAD`, estado local y alcance. No hacer reset, clean ni descartar cambios ajenos. Un commit solo NO acredita qué se publicó.
2. Comparar funcionalidad y contratos contra `contracts/operational_routes.json`. Incluye método y ruta; cambiar PUT por PATCH no es compatible por tener un nombre parecido. `backend/test_release_guard.py` falla si desaparece cualquier contrato aprobado.
3. Revisar cambios de `contracts/release_assets.json`: favicon y fuentes están fijados por SHA256. Una actualización intencional exige evidencia visual y revisión, no regeneración ciega del baseline.
4. Ejecutar `./scripts/verify_recovery.ps1 -BaseRef inkora_pse/main -RequirePostgres -PythonPath <python-del-entorno-de-pruebas>` desde el candidato confirmado en Git. La selección automática aplica las reglas de **Validación por alcance** de abajo; `-Mode Full` solo puede elevar el alcance. Para el perfil completo, las variables `INKORA_GRE_POSTGRES_URL`, `INKORA_QUOTE_POSTGRES_URL`, `INKORA_WORKER_POSTGRES_URL` e `INKORA_SUMMARY_POSTGRES_URL` deben identificar cuatro bases **locales, exclusivas y desechables**, con prefijos `inkora_gre_`, `inkora_quote_`, `inkora_worker_` e `inkora_summary_`. Sus fixtures eliminan tablas exclusivamente en esas bases. Nunca usar producción/staging de usuarios. El modo sin PostgreSQL sirve para desarrollo, NO para aprobar concurrencia. Los cambios en procesos fiscales también requieren validación en staging aislado según AGENTS.md; las pruebas locales no sustituyen esa validación.
   - La misma verificación ejecuta Playwright mediante `scripts/run_e2e_local.py`: crea una SQLite temporal, una contraseña aleatoria, inicia API y Vite únicamente en `127.0.0.1:8000/5173` y elimina sesión/base al terminar. La configuración no admite URLs remotas ni un bypass de producción.
   - El workflow `release-gate.yml` conserva el check requerido `verify`. Registra alcance, commit y árbol Git completo en el artefacto `release-validation-receipt`. En `main` puede reutilizar la validación exitosa de un PR ya integrado únicamente si el árbol completo probado coincide exactamente. El manifiesto se calcula otra vez. Si falta evidencia, está vencida, falla la API o cambia cualquier archivo, no se autoriza ese atajo. PostgreSQL real continúa siendo obligatorio cuando corresponde al perfil completo; CI no lo sustituye.
5. Revisar navegador con datos sintéticos, controles, permisos, PDF y errores de consola. No usar comprobantes reales para probar escritura, baja o reenvío.
6. Cuando cambia backend, esquema, Storage o configuración, verificar esquema remoto y Storage mediante lectura. Los cambios de presentación con backend idéntico y evidencia válida conservan la verificación anterior. No ejecutar migraciones por rutina. Si falta algo necesario, detener publicación y preparar un bloque de migración separado.
7. Para producción ejecutar `python scripts/release_guard.py check --require-current-main` y empaquetar con `package --require-current-main --approved-sha256 <huella> --destination tmp/<entrega>`. El remoto predeterminado es `inkora_pse`; otro requiere `--remote <nombre>`. Se obtiene `main` de nuevo, se exige igualdad exacta con HEAD y se rechaza cualquier cambio tracked, incluidas pruebas y herramientas. Un candidato antiguo se bloquea incluso si tiene el mismo árbol de archivos. Los archivos publicables sin seguimiento también se rechazan. Revisar la huella y preparar un destino NUEVO bajo `tmp`. El empaquetador usa una lista positiva de runtime, incluye `requirements-lock.txt` y excluye credenciales, scripts administrativos/destructivos, seeds, pruebas, auxiliares y fixtures. CI y los ensayos de empaquetado pueden omitir `--require-current-main`; eso no los convierte en autorizaciones de producción.
   - Los manifiestos nuevos declaran `hash_mode: canonical-text-v1`. Los archivos UTF-8 se identifican después de normalizar CRLF/CR a LF; los binarios continúan comparándose byte por byte. Así, un checkout Windows y uno Linux producen la misma identidad lógica sin ocultar cambios de contenido.
   - Los manifiestos históricos que no incluyen `hash_mode` se verifican como `raw-v1`, preservando su huella y contrato originales para rollback. No se les aplican retroactivamente los marcadores funcionales actuales y nunca se debe editar un manifiesto antiguo para convertirlo al formato nuevo.
8. Inmediatamente antes de cada publicación ejecutar otra vez `check --require-current-main` y `verify --destination tmp/<entrega>`: revisión y huella deben coincidir con el paquete aprobado. Si main avanzó, integrar y recalcular alcance/validaciones; no publicar el paquete anterior. No modificar ese paquete; cualquier cambio obliga a otra huella y otra validación. No utilizar scripts históricos de empaquetado con listas parciales.
9. Publicar API compatible y worker desde el mismo contenido; verificar arranque, OpenAPI y salud. **La API compila desde raíz; el worker conserva `rootDirectory=backend` y compila mediante el Dockerfile backend incluido en la misma huella.** Para el worker ejecutar `project_worker_release.py <paquete> tmp/<proyeccion-worker>`: verifica el manifiesto, copia únicamente el backend y genera en la raíz del bundle los adaptadores `Dockerfile` y `railway.json`. El adaptador declara explícitamente `run_emission_worker.py` y su servidor de salud; no debe depender de un start command heredado de Railway, porque una carga CLI podría iniciar Uvicorn y dejar detenido el procesador fiscal aunque `/health` responda. Publicar ese directorio completo con `railway deployment up ... --path-as-root`; no publicar directamente la subcarpeta `backend`. El ambiente y las variables del worker continúan siendo los configurados en Railway. Publicar frontend desde el paquete completo primero sin promoción automática y promoverlo cuando esté READY. No modificar variables fiscales como parte del deploy.
   - Los Dockerfiles de API y worker instalan el mismo `backend/requirements-lock.txt`; por eso resuelven versiones idénticas en Python 3.11. `backend/requirements.txt` se conserva como puente para desarrollo, pero no debe dependerse de la detección Railpack para producción. Las dependencias directas se documentan en `backend/requirements.in` y cualquier actualización exige regenerar y probar el lock.
10. Comparar `/health.delivery.content_sha256` del API con `/release.json` del frontend y con el manifiesto. Registrar IDs Railway API/worker y Vercel, hora, huella, revisión y resultados. La vieja variable `INKORA_RELEASE_ID` puede estar obsoleta: no sustituye la huella del contenido.
11. Validar en producción por lectura: cotizaciones, facturas, boletas, inventario, configuración, acciones y descargas autenticadas. Las acciones visibles no autorizan pruebas de emisión real. Revisión acotada de logs debe indicarse como tal, no como observación de 24 horas.

## Rollback

Guardar los IDs de la entrega anterior antes de promover. Revertir aplicación mediante los despliegues anteriores compatibles, nunca restaurar correlativos, facturas, inventario ni CDR para deshacer un deploy. Un rollback de datos no revierte documentos aceptados por SUNAT. Si API y frontend dejan de ser compatibles, detener promoción; no ocultar controles para disimular rutas ausentes.

## Validación por alcance

`scripts/release_scope.py` mantiene un mapa explícito de secciones y pruebas. No se decide por una etiqueta del PR ni por afirmar que un cambio es visual.

| Perfil | Selección y puertas |
| --- | --- |
| Visual | CSS limitado a la tabla de documentos: unitarias frontend, lint, build, bundle, navegación/permisos/móvil y pruebas de documentos/paginación. Revisión visual escritorio y móvil. |
| Frontend | Páginas o componentes conocidos: las mismas puertas y pruebas de todas las secciones afectadas. CSS global o componentes generales requieren toda la suite de navegador. |
| Completo | Backend, cálculos/utilidades, autenticación, emisión, dependencias, contratos, build, scripts, workflows, pruebas modificadas, archivos nuevos/eliminados/renombrados o rutas no reconocidas: backend, PostgreSQL local, frontend y toda E2E. |
| Documentación | Solo modificaciones de Markdown dentro de docs: controles del propio proceso y manifiesto. No publica la aplicación. |

- Los perfiles visual/frontend solo omiten la regresión backend si existe un recibo completo exitoso de **main** cuyo código backend, pruebas, dependencias, contratos y herramientas de validación tienen exactamente la misma huella Git que el candidato. Se comprueba el commit real del run y su árbol; un JSON local o el manifiesto runtime no son evidencia suficiente. Sin prueba válida se eleva a completo.
- La reutilización de PR en main exige run exitoso del mismo workflow/repositorio, PR integrado en main y árbol Git completo idéntico. Incluye scripts, pruebas y configuración que el manifiesto runtime no contiene. No se reutiliza solo por nombre de rama, hash runtime o similitud del diff.
- Los recibos caducan a los 30 días. La consulta se limita a los últimos 30 runs exitosos; evidencia ausente o errores provocan validación completa. `workflow_dispatch` siempre ejecuta completo.
- El runner focalizado admite únicamente specs existentes dentro de `frontend/e2e`; mantiene API/SQLite local aislada, credenciales temporales y limpieza. El plazo por prueba es 60 segundos para recorridos móviles de varias rutas; no cambian sus aserciones ni los timeouts de expectativas.
- Las modificaciones de este proceso se clasifican como completas. Nunca se aplica un perfil menor a su propia primera validación.
- El paquete canónico, identidad entre servicios, rollback y revisión posterior permanecen obligatorios para una publicación de aplicación. Un cambio exclusivo de CI/documentación/herramientas no requiere volver a desplegar el runtime si su contenido es idéntico.

## Límites del control

Las pruebas de contratos detectan pérdidas de rutas, no demuestran por sí mismas su comportamiento. Las huellas demuestran identidad, no ausencia de bugs. Por eso se necesitan pruebas de dominio, seguridad, PostgreSQL y navegador. No hay homologación fiscal real si solo se usaron respuestas simuladas. La automatización no impide que un operador la omita: el procedimiento de publicación debe exigir estas puertas y revisar cualquier modificación a sus baselines.

Los recibos de idempotencia de carga masiva se conservan en auditoría (`inventory_bulk`): no purgarlos como logs descartables, pues previenen aplicar de nuevo una operación repetida.

El baseline de producción comprende 223 operaciones. No incluye cinco contratos disponibles exclusivamente en modo local/test (PATCH/DELETE users e invocaciones fiscales `*-legacy`); exigirlos en producción sería reactivar rutas deliberadamente retiradas. Los tests de `test_legacy_frozen_gating.py` verifican esa separación.
